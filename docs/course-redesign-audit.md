# Public course redesign audit

Baseline: f7eec0bce9e74e5577d66ab30c5c422e60a44c2c.

Final effective public inventory: 45 topics (42 retained including orientation, plus recommendation systems, experimentation and the enterprise feature-platform case), 376 lesson sections, 309 optional checks, 129 activities, 9 code-typed activities, 206 lesson/activity visualization references and 250 reading records. All existing IDs remain; these counts are generated by `engine/test_course_catalog.cjs` rather than inferred from an older snapshot.

## Design contract

- Four recommended paths: ML Engineer, AI Engineer, Forward-Deployed Engineer, Staff/Technical Lead. Paths select an order, never restrict browsing or imply hiring success.
- Shared chapter journey: prerequisites and outcomes, brief explanation/diagram, curated external lesson, attempt before reveal, explain a trade-off, apply/failure case, record evidence and next review.
- All chapters remain available; stable course/topic/section/activity IDs and deep links remain intact. Existing completion is self-recorded progress, not certification.
- Learning modes: learn, explain, apply, test. Contextual cards should locate the existing sections, diagrams, exercises, question banks and sources rather than duplicate lessons.
- Sources need provider, format, access status and estimated study budget versus publisher runtime. Unknown access/runtime is explicit; do not invent a video.
- Public home, metadata, roadmap and course must stand alone; optional private packs/configuration stay excluded by the existing public build boundary.

## Initial findings

The course already has diagrams, revealable model answers, question banks, accessible labels, dark/light tokens and reduced-motion treatment. The main discoverability limitation is a flat track outline and MLE-only orientation/metadata. External readings appear immediately after key terms without format/access labels or prioritization.

Quiz options already rotate deterministically by section, but the renderer mutates its content copy and stores displayed positions. A new shuffle must decode legacy rotation and keep old stored selections intact; simply changing the display permutation would reinterpret answers.

Some requested factual corrections affect existing quiz wording. The compatibility guard intentionally rejects those edits. Implement an explicit versioned-question contract with fresh answer storage and a reviewed manifest; do not disable the guard or reset user progress.

Confirmed initial statistical corrections: accuracy versus ROC-AUC, prediction-error decomposition versus generalization gap, missing-data assumptions, and non-monotone precision. The five linked domain ledgers below resolve the supplied audits against effective current source.

## Validation
